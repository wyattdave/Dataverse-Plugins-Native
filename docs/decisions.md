# Decision register

Bounded record of choices made for the Phase 1 POC. Each entry states what was decided, why, and what would change it.

| ID | Decision | Rationale | Revisit when |
| --- | --- | --- | --- |
| D01 | **TypeScript on Node.js instead of the proposed C#/.NET 10.** | Requirement §1.2(2–3) proposes C# on `net10.0` for a new repository. No .NET SDK was installed on the development machine; the owner chose TypeScript on the installed Node 22 (2026-10-15). Contracts, gates, and tests follow the requirements unchanged; only the implementation language differs. | The team standardizes on .NET, or a Dataverse SDK dependency becomes necessary. Contracts are JSON and portable. |
| D02 | Target Node.js ≥ 22.12; recommend moving to Node 24. | Node 22 "Jod" is in maintenance LTS since 2025-10-21, EOL 2027-04-30. Node 24 "Krypton" is active LTS (EOL 2028-04-30). Source: nodejs/Release `schedule.json`, checked 2026-10-15. Node 22 was the installed runtime; the code uses no Node 22–specific APIs. | Before any non-POC use: raise `engines` to the active LTS. |
| D03 | Zero runtime npm dependencies; dev-only `typescript` and `@types/node` (versions resolved by npm, not pinned by guess). | §3 "Keep production dependencies minimal". Built-in `node:test`, `node:crypto`, `fetch` suffice. | Live auth needs an MSAL-style public-client library with an OS-backed cache. |
| D04 | **Snapshot-first; live reads blocked in the CLI.** | No approved public client ID or token provider exists. The trust-boundary transport is implemented and fake-tested but not wired; the CLI returns `LIVE_TRANSPORT_NOT_CONFIGURED` instead of guessing a "current environment". | An approved client ID and OS-backed token provider are supplied (U01). |
| D05 | Contract v1 numbers are safe integers only; fractions, exponents, `-0` rejected at parse time. | §7(4). Decimal formula values remain source text. | A contract needs non-integer numerics (would be a v2 contract). |
| D06 | Canonicalization `adapter.c14n/v1` = ordinal UTF-16 key sort, ECMAScript `JSON.stringify` string escaping, arrays in order. | Matches RFC 8785 behavior for the integer-only subset; golden output and hash cross-checked with .NET SHA-256. | Never silently; any change is a new canonicalization version. |
| D07 | `tableReferences` / `connectionReferences` are sets (sorted by logical name); **parameters are ordered**. | Parameter order significance in the native designer is unknown; treating it as ordered keeps reorders visible (flagged `BREAKING_CHANGE_REQUIRES_REVIEW`, impact `unknown`). | G0 evidence shows whether order is semantic. |
| D08 | Snapshots and plans carry formula **hashes only**, never source text. | §5 forbids logging code bodies; equality only needs hashes. Snapshots record which normalization produced the hash; mismatched normalization compares as `unknown`. | Never for logs. A private, protected source snapshot may be added for recovery (§9). |
| D09 | Offline environment classification is never trusted; effective class is always `unknown` in Phase 1. | §5: config/file claims are expectations, not proof; no authenticated management discovery route is implemented. | A documented authenticated route (e.g. Power Platform admin environment metadata) is implemented and tested. |
| D10 | Snapshot `source.mapping` only allows `unverified` in v1. | The platform-row → projection mapping (customapi / fxexpression / msdyn_function) is U03; a file cannot claim it is verified. | G0 evidence proves the mapping and a v2 snapshot contract is reviewed. |
| D11 | Microsoft-reserved prefixes (`ms*`, `adx`) and system solutions (`Default`, `Active`, `Basic`) are always rejected. | §5 "never alter managed Accelerator/Microsoft components, even if a namespace check appears to allow it". INFERENCE: prefix list is conservative, not exhaustive; managed state is checked separately. | Ownership is read from authenticated publisher/solution records. |
| D12 | v1 target allowlist is exactly one origin equal to the organization URL; public cloud (`*.crm*.dynamics.com`) only. | §5 singleton allowlist; sovereign clouds need their own authority/resource validation. | A sovereign-cloud profile is required. |
| D13 | Plan output (`--out`) never overwrites; created with `wx` and mode 0600. | Plans are immutable artifacts bound by `planHash`. | — |
| D14 | Journal state machine: `prepared → dispatching → completed \| failed-definite \| outcome-unknown`. `dispatching` is written durably before dispatch. | §8: a crash after `dispatching` means "potentially executed"; reconcile reports `outcome_unknown`. | A proven server idempotency/retry contract exists for a specific operation. |
| D15 | Added an `approve` command (not in §6 table) that always refuses Phase 1 plans. | Demonstrates §7(13) "reject draft/ineligible plans" without issuing any approval artifact. | Phase 2 approval flow with retained private attestation. |
| D16 | Approval verification always adds `APPROVAL_ATTESTATION_UNVERIFIED`. | Hashes detect tampering but anyone can recompute them; the approver is not yet authenticated (review finding). | A trusted local attestation (OS-protected signing key or protected approval record) authenticates the approver. |
| D17 | Approved operation set must equal the plan's operation set exactly; duplicate IDs rejected. | Prevents a partial approval from authorizing a multi-operation apply (review finding). | — |
| D18 | `planId` uses a timestamp-free evidence projection (excludes `snapshotAcquiredAt` and whole-snapshot hash); `planHash` still binds both. | §7(9): semantic ID excludes timestamps; a refreshed identical snapshot keeps its `planId` (review finding). | — |
| D19 | `reconcile` never reports `succeeded` from journaled completions; it caps at `blocked` (`READ_BACK_REQUIRES_LIVE_READS`). | The journal is a local, unkeyed record; §9 requires authoritative identity and complete graph verification (review finding). | Live read-back with correlation evidence exists. |
| D20 | Read-transport continuations must keep the original path and query options and may only add `$skiptoken`/`$skip`; bodies are streamed with a byte cap; the constructor enforces full target policy. | §5 trust boundary: a same-origin nextLink must not pivot to another entity; large bodies must not exhaust memory (review finding). | A proven Dataverse paging contract requires other options. |
| D21 | **A basic local UI was added at the owner's request (2026-10-15), although §1.1 puts UI out of scope for the MVP.** It is constrained to the §11/E17 rules: typing only triggers an offline validate (parse/check), every other operation is an explicit button, and all gated operations stay blocked. It runs on 127.0.0.1 only, on demand (`dv-native ui`), not as an always-on service; there is no persistence and no third-party code. | The owner asked for open/type/run in a window. Reusing the same operations layer keeps one policy and gate path for every host. | The team wants a VS Code extension or a hosted UI. A hosted, multi-user UI would need authentication and a separate review. |
| D22 | **Owner decision (2026-10-15): add a simple four-step flow (create → check → environment → deploy) for instant *and* automated plug-ins, overriding the Phase 1 "all writes blocked" rule for this flow.** Auth and every Dataverse call go through the Power Platform CLI (`pac auth`, `env list`, `env fetch`, `solution pack`, `solution import`); dv-native never handles tokens. | Solution import is Microsoft's supported ALM path; the component layout is taken from Microsoft's public contoso-real-estate-power-platform solution source instead of guessed private endpoints. pac already owns sign-in and token storage (CAP-cli pattern), removing the need for an approved client ID. | Live import shows a different required layout, or Microsoft documents a direct API. |
| D23 | **Owner decision (2026-10-15): Production and Default environments are allowed.** The environment type is shown (when `pac env list` prints it) and included in the UI confirmation, but never blocks. | Microsoft labels Functions preview/"not for production"; that is guidance, not a platform restriction, and the owner accepts the risk. Supersedes the §1.1 production hard-block for the four-step flow only. | The org adopts a policy requiring a gate (e.g. an approval or a separate prod profile). |
| D24 | Automated step ids are reused from the environment (FetchXML via `pac env fetch`) or derived deterministically from the unique name; deploy fails closed when more than one step is linked. | Prevents duplicate triggers on redeploy, including plug-ins first created in the maker portal. | — |
| D22 | A host-neutral operations layer (`src/app/operations.ts`) takes document **text** and is shared by the CLI and UI. Each operation declares its required/optional documents; unexpected documents, stray options, and oversize inputs fail closed. | §3: "core MUST NOT know CLI, future skill, or UI details; all callers use the same typed contracts and policies." | — |
| D23 | UI JSON formatting is token-based (re-indent only); the spec form refuses to edit JSON that has syntax errors or duplicate keys. | `JSON.parse`-based formatting would silently drop duplicate keys and could change values, hiding errors the strict adapter parser reports. | — |
